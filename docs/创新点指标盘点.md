## 1. 盘点方法与边界

### 1.1 只看三类真相源

1. **确定性引擎**：`engine/` 下纯函数返回值（如 `recommend.score_job()`、`cert_guide.active_reminders()`、`metrics.summarize_latency()`）。
2. **数据库实数**：MySQL 表行数/字段非空率、DuckDB `推荐日志` 行数与 JSON 理由数组。
3. **测试/代码事实**：pytest 运行汇总、`agents/tools.py` 注册表长度。

不采用：模型输出、历史文档快照、示例值、行业宣传数字。

### 1.2 三条硬口径

- **缺失不填 0**：查不到或无事件链，返回 `null` + `available=false`，卡片显示“尚未采集/无此数据”。
- **时间必须带 `as_of`**：提醒数、推荐条数、耗时都是滚动数据，页面不得缓存成静态值。
- **口径写在卡上**：同一数字有多个算法时，只选一个主口径，其余放 tooltip/说明，不混用。

### 1.3 本次实测环境

- Windows 11 + PowerShell，Python 3.12（`D:\qihang\.venv`）。
- MySQL 8.0.21 / 库 `qihang`；DuckDB 文件 `D:/qihang/data/analytics.duckdb`。
- 所有查询均只读（`SELECT` / DuckDB `read_only=True`），未写业务表。

## 2. 六个点名指标逐条核实

### 2.1 推荐理由条数

**口径（建议主口径）**

> 「推荐理由条数」= DuckDB `推荐日志` 中 `命中项` 与 `缺口项` 两个 JSON 数组的元素总数（条次）；另给“推荐记录数”和“去重理由文本数”，三者不混用。

**实测值**

| 项 | 值 | 说明 |
|---|---:|---|
| 推荐记录数 | **5,737** | 一行 = 一名学生 × 一个岗位的一次打分 |
| 命中理由条次 | **16,238** | `json_array_length(命中项)` 求和 |
| 缺口理由条次 | **15,387** | `json_array_length(缺口项)` 求和 |
| 理由总条次 | **31,625** | 16,238 + 15,387 |
| 去重理由文本 | **230 种**（命中 127 + 缺口 103） | 模板化生成，条次远大于种类 |
| 每条推荐平均理由 | **5.51 条**（命中 2.83 + 缺口 2.68） | 31,625 ÷ 5,737 |
| 三段式完整率 | **5,737/5,737 = 100%** | 每行都有命中项、缺口项、非空建议 |
| 协同过滤覆盖 | **4,514/5,737 = 78.68%** | `协同得分` 非空的行占比 |
| 覆盖学生数 | **19** | 只覆盖演示/测试调用过的学生，不是全校 10,000 人 |
| 覆盖岗位数 | **158** | 去重岗位编号 |
| 时间范围 | 2026-10-27 14:59:10 ~ 2026-11-22 18:30:41 | 最近 7 天 1,902 条 |
| 引擎版本 | hybrid-v1 5,551；v1.0 186 | 版本不同，分数不可直接横比 |

**取数位置**

- 表：DuckDB `推荐日志`（`学号`、`岗位编号`、`最终得分`、`命中项`、`缺口项`、`建议`、`协同得分`、`引擎版本`、`创建时间`）。
- 生成：`engine/recommend.py::score_job()` 返回 `hit_items` / `gap_items` / `action_items`；`engine/recommend.py::recommend()` 组装。
- 落库：`engine/store.py::write_recommend_log()`（`DuckDbStore`）。
- 纯函数汇总：`engine/metrics.py::summarize_recommend()`（总数/学生数/均分/CF 覆盖率/平均命中缺口）。

**验证方式**

```sql
       SUM(json_array_length("缺口项")) AS gap_items,

```

```python

```

配套测试：`tests/test_recommend.py`、`tests/test_metrics.py::test_summarize_recommend_parses_json_strings`。

**展示建议**

- 主数字用 **“31,625 条可解释理由”**，副标题 “5,737 条推荐 · 每条平均 5.51 条 · 去重 230 种”。
- 或主数字用 **“5,737 条推荐”**，tooltip 展开命中/缺口拆分。
- 禁止写成“19 名学生”当覆盖规模；只能说“当前推荐日志样本含 19 名学生”。

**已知边界**

- 同一学生重复调用会产生大量行：`AI20230001` 一人 4,022 条，第二名 922 条，最少 5 条。**不能把 5,737 当独立推荐次数**。

- 表里没有租户编号：教师端聚合必须先按 `学生` 表圈定租户/任教范围，不能直接 `GROUP BY 学号`。
- 5,737 包含测试/演示调用写入；对外表述建议加“演示数据快照”。

### 2.2 依据覆盖率

先拆成三个不同口径，避免一个词被误用：

| 口径 | 定义 | 实测 | 能不能当“依据覆盖率”主卡 |
|---|---|---|---|
| A. 外部事实字段级覆盖率 | 记录同时有“来源链接”和“核实/采集日期”的比例 | **619/619 = 100%** | **可以**，推荐主卡 |
| B. 推荐理由完整率 | 推荐记录同时有命中项、缺口项、建议的比例 | **5,737/5,737 = 100%** | 可以作为副卡，但它是“完整率”不是“覆盖率” |
| C. 协同过滤覆盖率 | 推荐记录中 `协同得分` 非空比例 | **4,514/5,737 = 78.68%** | 不建议上主卡，专业口径太窄 |
| D. 回答引用留痕率 | assistant 消息带 `引用` JSON 的比例 | **30/341 = 8.80%** | 不建议叫“覆盖率”，叫“引用留痕率” |

#### A. 外部事实字段级覆盖率（建议主卡）

**口径**

> 在对外事实表中，`来源链接/原文链接/投递链接` 非空 **且** `核实日期/采集时间/最近发现时间` 非空的记录数 ÷ 该类记录总数。四类表合并计算。

**实测明细**

| 表 | 总数 | 有链接 | 有日期 | 双全 | 日期字段含义 |
|---|---:|---:|---:|---:|---|
| `考证目录` | 8 | 8 | 8 | **8/8** | `核实日期`（人工核实，统一 2026-11-19） |
| `招考公告` | 43 | 43 | 43 | **43/43** | `最近发现时间`（抓取时间，不是人工核实） |
| `招聘岗位` | 334 | 334 | 334 | **334/334** | `最近发现时间`（抓取时间） |
| `面试题库` | 234 | 234 | 234 | **234/234** | `采集时间`（入库日期） |
| **合计** | **619** | **619** | **619** | **619/619 = 100%** | — |

补充：题库 234 条全部 `校验状态='verified'`、`启用=1`；考证目录 8 条全部 `来源链接 LIKE 'http%'` 且有核实日期。

**取数位置**

- MySQL：`考证目录`（`来源链接`、`核实日期`）、`招考公告`（`原文链接`、`最近发现时间`）、`招聘岗位`（`投递链接`、`最近发现时间`）、`面试题库`（`来源链接`、`采集时间`）。
- 字段定义：`db/cert_tables.sql`、`db/recruit_tables.sql`、`db/question_bank.sql`。
- 前端现有展示：`CertHub.vue` 的目录卡（本轮不改 `web/`）。

**验证方式**

```sql
SELECT '考证目录' AS src, COUNT(*) AS total,
       SUM(`来源链接` IS NOT NULL AND `来源链接` <> '') AS has_link,
       SUM(`核实日期` IS NOT NULL) AS has_date
FROM `考证目录`
UNION ALL
SELECT '招考公告', COUNT(*),
       SUM(`原文链接` IS NOT NULL AND `原文链接` <> ''),
       SUM(`最近发现时间` IS NOT NULL)
FROM `招考公告`
UNION ALL
SELECT '招聘岗位', COUNT(*),
       SUM(`投递链接` IS NOT NULL AND `投递链接` <> ''),
       SUM(`最近发现时间` IS NOT NULL)
FROM `招聘岗位`
UNION ALL
SELECT '面试题库', COUNT(*),
       SUM(`来源链接` IS NOT NULL AND `来源链接` <> ''),
       SUM(`采集时间` IS NOT NULL)
FROM `面试题库`;
```

**展示建议**

- 主数字：**“619 条外部事实，100% 带来源链接与日期”**。
- 必须加限定词：**“字段级”**，并注明“招聘/招考日期为抓取时间，不等同人工核实”。
- 不能写“100% 事实准确”或“链接全部可打开”：本轮只校验字段非空，**没有逐条 HTTP 200 校验，也没有内容比对**。

#### B. 推荐理由完整率

**口径**：推荐记录同时具备 `命中项`（非空数组）、`缺口项`（非空数组）、`建议`（非空字符串）的行占比。

**实测**：5,737/5,737 = **100%**。但这说明的是“模板字段齐全”，不等于“理由一定正确”；理由文本由确定性规则生成，正确性依赖输入成绩/技能/岗位标签。

**验证**：

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (
         WHERE json_array_length("命中项") > 0
           AND json_array_length("缺口项") > 0
           AND "建议" IS NOT NULL AND "建议" <> ''
       ) AS complete
FROM "推荐日志";
```

#### D. 回答引用留痕率（供“可追溯”叙事，不要叫准确率）

**口径**：`对话消息` 中 `角色='assistant'` 且 `引用` JSON 非空的消息数 ÷ assistant 消息总数。

**实测**：**30/341 = 8.80%**；按工具拆：`kb_search` 22 条、`web_search` 8 条。绝大多数普通问答没有引用，不能包装成“回答都可追溯”。

**取数**：MySQL `对话消息`.`引用`（结构 `[{doc_id,title,page,chunk_no,score}]`）、`对话消息`.`工具`。

**验证**：

```sql
SELECT COUNT(*) AS assistant_total,
       SUM(`引用` IS NOT NULL) AS cited,
       ROUND(SUM(`引用` IS NOT NULL) / COUNT(*), 4) AS cited_rate
FROM `对话消息`
WHERE `角色` = 'assistant';
```

### 2.4 三阶段提醒数

**口径**

> 三阶段 = 考证中心 `active_reminders` 的三个提醒阶段：0=即将开放报名≤14 天；1=报名中；2=考前≤14 天。  
> 「三阶段提醒数」= 调用 `engine.cert_guide.active_reminders(as_of)` 返回的条目数，按阶段拆分；**不是固定 3 条**。

**实测值（as_of 2026-11-22）**

| 项 | 值 | 说明 |
|---|---:|---|
| 当天活跃提醒 | **1 条** | 阶段 2：中小学教师资格考试（NTCE），13 天后开考 |
| 阶段 0（即将报名） | **0 条** | 当天无“14 天内开放报名”的证书 |
| 阶段 1（报名中） | **0 条** | 当天无“正在报名”的证书 |
| 阶段 2（临近考试） | **1 条** | `cert_id=5`，`id=1000000502` |
| 水位 `watermark_max` | **1000000502** | 学生已读后本阶段不再提醒；进入下一阶段 id 增大，会再提醒 |
| 考证目录总量 | **8 条** | 全部有来源链接 + 核实日期 |
| 未来 60 天三阶段条目日累计 | **105 条次**（阶段 0：28；阶段 1：33；阶段 2：44） | 同一天可能 1~3 条；涉及证书 2/2/3 本 |

### 2.6 平均响应耗时

这个指标有 4 种算法，先列清楚，再选主口径。**不同口径不能混着说。**

| 口径 | 数据源 | 样本 | 均值 | P50 | P95 | 最大值 | 适用 |
|---|---|---:|---:|---:|---:|---:|---|
| A. 单轮 AI 回答耗时 | `对话消息.耗时毫秒`（assistant） | 340 | **9,055.3ms** | **2,651ms** | **41,144ms** | 100,379ms | **推荐主口径**（用户感知的回答生成） |
| B. 成功 chat 接口耗时 | `审计日志` 动作 `POST /chat` 且 status 2xx | 120 | **3,235.6ms** | 2,140.5ms | 13,821.1ms | 28,453.7ms | 接口性能副口径 |
| C. agent.chat 审计耗时 | `审计日志` 动作 `agent.chat` 的 `duration_ms` | 364 | 5,734.0ms | 91.6ms | 29,064.3ms | 61,137.3ms | 不建议上卡（双峰，含模板/缓存快路径） |
| D. `/chat/metrics` 近 7 天 | `审计日志` 动作 `agent.chat`，教师端接口 | 417 | 5,671.8ms | — | — | — | 可复用，但只给教师、只给均值 |

> A 的时间窗为 2026-10-27 ~ 2026-11-19；B/C 取 2026-11-20 之前的干净窗口，避开测试运行写入。

**为什么主口径选 A**

- 它是“一个 assistant 回答实际花了多久”，与用户感知一致，且每条消息都落库。
- 均值 9.06s 被少量长任务拉高（`brain` 工具平均 53s），所以**卡片主数字用 P50=2.65s，P95=41.14s 作为长尾**；均值放 tooltip，避免“平均 2.65s”的偷换。
- B 是 HTTP 层耗时，含排队/序列化，且只统计 2xx；适合做接口性能，不适合讲“AI 回答速度”。

**取数位置**

- 表：MySQL `对话消息`.`耗时毫秒`（assistant 行）、`引用`、`工具`；`对话会话` 提供租户/角色。
- 表：MySQL `审计日志`.`详情` JSON 的 `duration_ms`、`status`；中间件在 `app/main.py` 统一写入。
- 纯函数：`engine/metrics.py::summarize_latency()`（count/avg/p50/p95/max，最近秩分位数）。
- 现有接口：`GET /chat/metrics`（教师，近 7 天，返回 `avg_duration_ms` / `degraded_rate` / `like_rate`）。

**验证方式**

```sql
SELECT COUNT(*) AS n, ROUND(AVG(`耗时毫秒`), 1) AS avg_ms
FROM `对话消息`
WHERE `角色` = 'assistant' AND `耗时毫秒` IS NOT NULL
  AND `创建时间` >= '2026-10-27' AND `创建时间` < '2026-11-20';
```

```python
from engine.metrics import summarize_latency
# 传入耗时列表，断言 count/avg_ms/p50_ms/p95_ms/max_ms
print(summarize_latency([...]))
```

**展示建议**

- 主卡：**“单轮回答 P50 2.65s”**，副标题“P95 41.14s · 均值 9.06s · 340 条（截至 2026-11-19）”。
- 若面向教师讲接口性能：**“成功请求平均 3.24s / P95 13.82s（120 条）”**。
- 禁止写“平均 2.65s”：2.65s 是中位数，不是均值。
- 禁止用 `agent.chat` 的 P50 91.6ms 当“AI 回答耗时”：那批样本里混有模板/缓存快路径，分布双峰。

**已知边界**

- `对话消息.耗时毫秒` 包含 LLM 生成等待，不含前端渲染/网络；不是端到端时延。
- `/chat/metrics` 只筛 `agent.chat`，没有 `status` 过滤，失败请求也会进均值；上卡前建议补 2xx 过滤或明确“含失败”。
- 测试运行会向真实库写审计/对话数据；滚动窗口统计要排除测试窗口，或给测试加独立库。
- `审计日志.详情` 是 JSON，字段没有 schema 版本；`agent.chat` 1,669 行里只有 364 行带 `duration_ms`，缺失不是 0。

## 9. 已知问题与下一步

### 9.1 数据模型缺口（按优先级）

1. **`推荐日志` 无租户编号、无请求号、无 `action_items`**：教师端聚合要先圈学生范围；重复调用无法去重；下一步动作不能逐条回放。建议后续加 `租户编号`/`请求号`，或只保留“每人每岗最新一条”。
2. **`审计日志.详情` 无 schema 版本**：`duration_ms` 在 `agent.chat` 中只有 364/1,669 行有值，统计时要显式排除缺失，不能补 0。
3. **测试结果不落库**：无法做在线“测试通过数”。若主控要上卡，建议 pytest `--junitxml` 产物入库或对象存储 + `/innovation/test-result` 只读接口。
4. **知识库文档来源地址 0/33**：都是上传文件；引用可回溯到文档/页码/块号，但没有原始 URL。对外说“可追溯”要限定到“文档/页码/块号”。
5. **`岗位` 表无状态列**：`/job/stats.open` 是伪在招；必须用 `招聘岗位.状态`，并带租户。
6. **依据覆盖率只是字段级**：619/619 只证明“链接/日期字段非空”，未做链接可打开、内容一致的抽检。若要升级为“可核对率”，需另做 HTTP 200 + 内容抽样审计。

### 9.2 上卡前的三条验收

- [ ] 每个数字能指回表字段或引擎函数，且响应带 `as_of`、`scope`、`source`。
- [ ] 缺失显示 `available=false` / “尚未采集”，不出现 0 或示例值。
- [ ] 学生只本人、教师只租户/任教范围；接口不接受前端传 `student_id`。

### 9.3 本轮未做

- 未改 `web/`、未改部署、未新增业务表、未实现 `/innovation/*` 接口。
- 未做外部链接 HTTP 校验、未做推荐理由人工抽检、未做性能压测。
- 未提交测试用的临时脚本；`logs/innovation_metrics_snapshot.json` 为本地快照，已随 `logs/` 忽略。
